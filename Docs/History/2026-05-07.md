## Сессия: Возврат legacy runtime alignment без `LLM`

### Что сделано

- отключён автозапуск `LLM alignment` после:
  - rebuild quality
  - повторной сборки книги
- reader/runtime path переведён с `LLM` обратно на цепочку:
  - `SimAlign exact`
  - затем `legacy fallback` через `build_word_mappings(...)`
- `legacy fallback` скорректирован так, чтобы:
  - не пропускать весь сегмент целиком
  - дозаполнять только те слова, которые не получили span через `SimAlign`
- из effective/detail логики убран специальный runtime-режим:
  - `runtime_llm_alignment`

  - `/books/rebuild-llm-alignment`
  теперь возвращает ошибку, чтобы UI и скрипты не запускали `LLM`-контур в legacy-режиме

### Что не трогалось

- таблица `segment_llm_alignments` и поля `llm_alignment_*` в БД не удалялись
- `SimAlign` sidecar сохранён как промежуточный non-LLM слой

### Зачем так

- это мягкий откат поведения без опасной миграции БД
- книги и существующие persisted структуры продолжают открываться
- основной runtime снова работает без зависимости от `LLM`-alignment контура

## Сессия: Архитектурный вывод по будущему alignment-контуру LEXO

### Источник

- зафиксирован отдельный архитектурный вывод из рабочего обсуждения в чате
- это не реализация и не код, а целевая схема того, как должен выглядеть хороший pedagogical alignment поверх уже существующего `Marian + SimAlign` контура

### Главный вывод

- alignment не должен мыслиться как `word = word`
- правильная базовая единица:
  - `EN unit -> RU meaning span`
- `unit` может быть:
  - одиночное слово
  - phrase
  - absorbed grammar word
  - omitted word

### Что признано правильной архитектурой

- `Marian` остаётся переводчиком сегмента
- `SimAlign` остаётся не финальной истиной, а одним из сигналов
- между raw `SimAlign` и UI должен появиться отдельный resolver-слой
- `tap 2` словарь не должен быть самим aligner-ом, но его данные могут использоваться как `dictionary prior`

### Какие сигналы должен учитывать хороший aligner

- `simalign / embedding signal`
- `dictionary signal`
- `position prior`
- `grammar / POS compatibility`
- `phrase bonus`
- `context support`

### Что важно для LEXO

- цель не академический perfect alignment
- цель: стабильный pedagogical tap mapping
- alignment должен уметь возвращать не только `aligned`, но и:
  - `phrase`
  - `absorbed`
  - `omitted`
  - `rejected`

### Предлагаемый новый persisted contract

### Предлагаемые новые модули

- `engine/alignment_units.py`
- `engine/alignment_features.py`

Где:
- `SimAlign` = raw signal

### Что считать в score v1

- `simalign_score`
- `dictionary_score`
- `position_score`
- `grammar_score`
- `phrase_score`

Итоговый `confidence` трактовать не как “настоящую вероятность”, а как устойчивый рейтинг качества связи.

### Что особенно важно

- grammar/function words не нужно force-match-ить любой ценой

## Сессия: Детальный план модулей для будущего resolver-контура LEXO

### Цель

- не заменить всё сразу, а ввести новый слой:
  - `Marian` делает перевод
  - `SimAlign` даёт сырой сигнал
  - новый resolver собирает итоговое pedagogical alignment
  - UI получает уже не raw span, а нормализованный `unit -> meaning span`

### Новый persisted contract

- нужен не `word -> token`, а resolved JSON формата:

```json
{
  "segment_id": "seg_123",
  "units": [
    {
      "source_text": "bus driver",
      "source_start": 1,
      "source_end": 2,
      "target_text": "водитель автобуса",
      "target_start": 0,
      "target_end": 1,
      "type": "phrase",
      "confidence": 0.94,
      "signals": {
        "simalign": 0.81,
        "dictionary": 0.92,
        "position": 0.88,
        "grammar": 1.0,
        "phrase": 1.0
      },
      "status": "aligned"
    },
    {
      "source_text": "the",
      "source_start": 0,
      "source_end": 0,
      "target_text": null,
      "target_start": -1,
      "target_end": -1,
      "type": "absorbed",
      "confidence": 0.93,
      "signals": {
        "grammar": 1.0
      },
      "status": "absorbed"
    }
  ]
}
```

- именно это рассматривается как целевой новый persisted alignment format

### Новый слой

- основной новый файл:
  - `engine/alignment_resolver.py`
- он:
  - не переводит
  - не рендерит UI
  - только получает сигналы и выбирает лучший mapping

### Входы resolver-а

- `segment source text`
- `segment target text`
- `source words`
- `target tokens`
- raw `SimAlign links`
- `source POS/lemma`
- `target POS/lemma`
- `dictionary candidates`
- `phrase candidates`

То есть нужен не один helper, а небольшой alignment pipeline.

### Предлагаемое разбиение на модули

#### `engine/alignment_units.py`

- отвечает за unit building:
  - одиночные слова
  - phrase candidates
  - special grammar words

Примеры unit:
- `bus driver`
- `wake up`
- `good night`
- `to`
- `opened`

#### `engine/alignment_features.py`

- считает признаки для пары `source_unit -> target_span`:
  - `simalign_score`
  - `dictionary_score`
  - `position_score`
  - `grammar_score`
  - `phrase_score`
  - `context_score`

#### `engine/alignment_resolver.py`

- собирает кандидатов
- считает score
- выбирает победителей

#### `engine/alignment_contract.py`

- dataclass/payload helper-ы для итогового resolved JSON

### Откуда брать грамматику

- для `v1` не нужен тяжёлый NLP
- минимально достаточно:
  - EN:
    - текущее `source_pos`
    - lemma, если уже есть
  - RU:
    - грубая классификация токенов:
      - `nounish`
      - `verbish`
      - `adjish`
      - `function`

- более глубокую RU морфологию можно добавлять позже отдельным этапом

### Как строить score

- не как “магия”, а как сумма стабильных сигналов
- рабочая `v1`-формула:

```text
final =
  0.35 * simalign_score +
  0.25 * dictionary_score +
  0.15 * position_score +
  0.15 * grammar_score +
  0.10 * phrase_score
```

- веса не должны быть академическими
- они должны быть понятными, стабильными и дебажимыми

### Что такое `position_score` для нас

- это мягкий приоритет
- идея:
  - source unit на 40% длины сегмента
  - target span на 45% длины сегмента
  - значит pair хорошая
- чем ближе относительные позиции, тем выше score
- это bonus, а не жёсткое правило

### Что делать с phrase-first

- это обязательный слой
- порядок должен быть такой:
  1. построить phrase candidates
  2. попытаться матчить phrase
  3. только потом матчить одиночные слова

Иначе будут системно ломаться:
- `bus driver`
- `wake up`
- `look out`

### Что делать с grammar words

- это отдельный тип результата
- их не нужно force-match-ить любой ценой
- нужны статусы:
  - `aligned`
  - `phrase`
  - `absorbed`
  - `omitted`
  - `rejected`

- это важнее, чем пытаться дать перевод каждому слову

### Conflict resolution

- resolver должен выбирать набор совместимых links, а не лучший link по одному слову
- если два source unit хотят один target span:
  - phrase сильнее слова
  - content word сильнее function word
  - высокий `dictionary + grammar + simalign` сильнее низкого
  - короткий чистый span сильнее длинного грязного

- для `v1` достаточно:
  - greedy ranking
  - запрет конфликтующих победителей

- не нужно сразу тащить:
  - Hungarian matching
  - CRF
  - heavy global optimization

### Как встроить это мягко

#### Сейчас

- `engine/runtime_simalign_clean.py` читает raw `SimAlign`

#### Потом

- rebuild path считает resolved alignment и сохраняет его
- runtime сначала читает `resolved_alignment`
- если его нет, временно падает в raw `SimAlign`

- rollout можно сделать мягким, без слома текущего reader

### Новый persisted слой

- логично добавить новую таблицу, а не портить старую сразу
- предлагаемый вариант:
  - `segment_resolved_alignments`

Поля:
- `segment_id`
- `resolver_version`
- `alignment_json`
- `created_at`

Это позволит:
- сравнивать версии resolver-а
- кэшировать результат
- не ломать старые raw alignment данные

### Этапы внедрения

1. Сделать только resolver contract и persisted JSON, без UI-переключения
2. Сделать `v1 resolver`:
   - phrase detection
   - dictionary score
   - grammar score
   - position score
   - absorbed logic
3. Прогнать на 1-2 книгах и сравнить:
   - raw `SimAlign`
   - resolved output
4. Подключить runtime reader к resolved layer
5. Оставить raw `SimAlign` как fallback/debug

### Чего делать не надо

- не делать `LLM alignment`
- не выкидывать `SimAlign`
- не делать full-text alignment
- не смешивать `tap 2` dictionary lookup с runtime alignment напрямую
- не строить giant linguistic engine на первом проходе

### Итоговая архитектура

- `engine/translator.py`
- `engine/alignment_simalign.py`
- `engine/dictionary_lookup.py`
- `engine/alignment_units.py`
- `engine/alignment_features.py`

Где:
