## Сессия: Диагностика провала retry на кейсе `He eats eggs and toast.`

### Что зафиксировано по текущему коду и данным

- QA проблему видит, но чинить её не умеет

#### Конкретно по сегменту `He eats eggs and toast.`

Из БД:

- `source_text = He eats eggs and toast.`
- `target_text = Он едит яйца и тосты.`
- `quality_status = fail`
- `retry_reason_flags = ["ru_spelling_error"]`
- `decision_status = retry_required`
- `translation_attempt_count = 3`
- `candidate_count = 3`
- `winner_reason = base_candidate_kept_after_retry`
- `back_translation = ""`

Итог по этому кейсу:

1. плохой перевод получен
2. QA его правильно пометил как плохой
3. сделаны 3 попытки
4. но в итоге остался тот же плохой вариант

#### Как это работает в коде

В [engine/storage.py](/mnt/d/Programs/LEXO/engine/storage.py) `_select_segment_translation(...)`:

1. строит `base_payload`
2. если `_requires_retry(base_payload)` истина, а других моделей нет
3. делает повторный `translate_segment_batch(...)` до `MAX_SINGLE_MODEL_ATTEMPTS = 3`
4. каждый новый вариант оценивает
5. если новый кандидат не лучше, оставляет старый

То есть retry действительно запускается.

#### Почему retry не чинит проблему

Retry сейчас:

- берёт ту же модель
- с теми же параметрами
- с тем же входом
- без post-correction
- без словаря
- без другого decode-profile
- без специального prompt
- без back-translation

И поэтому Marian выдаёт тот же результат.

Вывод:

- retry формально есть
- но механизма получения нового текста нет

#### Почему QA видит ошибку

В [engine/qa_ru_quality.py](/mnt/d/Programs/LEXO/engine/qa_ru_quality.py) `evaluate_ru_quality(...)`:

- делает `analyze_ru_text(target_text)`
- потом `_detect_spelling_like_errors(...)`
- если слово неизвестно для `pymorphy3`, ставит:
  - `ru_spelling_error`

Для `едит` это срабатывает правильно.

#### Почему back не помогает

Сейчас `back_translation = ""`.

После фикса runtime на одной модели и запрета других языковых моделей [engine/storage.py](/mnt/d/Programs/LEXO/engine/storage.py) в `_get_back_translation_provider(...)` больше не находит provider для пары `ru -> en`, потому что текущий Marian поддерживает только `en -> ru`.

Итог:

- `EN -> RU -> EN` в этом runtime фактически не работает
- semantic/verb loop для этого сегмента отсутствует

Но в этом кейсе это не главное: орфографическую ошибку QA и так уже видит без back-translation.

#### Почему всё равно сохраняется плохой перевод

Storage сейчас живёт в такой логике:

- если лучший кандидат всё равно плохой,
- его всё равно сохраняют,
- просто с:
  - `fail`
  - `retry_required`
  - `alignment_confidence = 0`

То есть pipeline умеет:

- “понять, что сегмент плохой”

Но не умеет:

- “сделать сегмент хорошим”

#### Что из этого следует

На этом кейсе причина не в том, что QA “не распознал”.

Причина в том, что после распознавания у системы нет repair-слоя.

Сейчас у неё нет:

1. другого профиля декодирования
2. другой модели
3. словарного repair
4. орфографического post-correction
5. принудительного reject без сохранения

Итоговая схема по этому месту сейчас такая:

- `translate`
- `detect error`
- `retry same thing`
- `get same thing`
- `save bad result`

### Почему нет другого варианта перевода

Сейчас одновременно выполнены оба условия:

1. другая языковая модель отключена
2. та же Marian детерминированная и не умеет дать новый вариант тем же вызовом

Поэтому:

- back-translation нет
- альтернативного кандидата по смыслу почти нет

Короткий вывод:

- `EN -> RU` работает
- `RU -> EN` почти нет
- другого осмысленного варианта перевода тоже почти нет

Проблема сейчас в том, что системе неоткуда взять второй осмысленный кандидат.
