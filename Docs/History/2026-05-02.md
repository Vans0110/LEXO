### Ключевая находка: реальный runtime source для `tap #1`

У каждой книги в приложении есть:

- `meta.json`
- `toc.json`
- `pages/*.json.gz`

Именно `pages/*.json.gz` оказались runtime-источником истины для `tap #1`.

### Подтверждённый формат page payload

На нескольких книгах и страницах подтверждён единый формат:

```json
{
  "tokens1": [["The",""," ",0,null],["Sunny",""," ",0,100],["Morning","","",1,100]],
  "tokens2": [["Солнечное",""," "],["утро","",""]],
  "sentences": [0],
  "version": 2,
  "translator": "google_mobile",
  "footnotes1": [],
  "footnotes2": []
}
```

Подтверждённая интерпретация полей:

- `tokens1[i] = [text, left, right, targetIndex, score]`
- `tokens2[j] = [text, left, right]`

Где:

- `text` — токен
- `left` — левый префикс перед токеном
  - например открывающая кавычка
- `right` — хвост после токена
  - пробел
  - пунктуация
  - перенос строки
- `targetIndex` — индекс target-токена в `tokens2`
- `score` — внутренний маркер типа/качества соответствия

Подтверждённые примеры:

- `["Sunny",""," ",0,100] -> tokens2[0] = "Солнечное"`
- `["Morning","","",1,100] -> tokens2[1] = "утро"`
- `["The",""," ",0,null] -> tokens2[0] = "Солнечное"`
- `["wakes",""," ",5,100]`
- `["up",""," ",5,null]`
  - оба указывают на `просыпается`

### Что это доказывает про `tap #1`

- `tap #1` не считает alignment в момент клика
- `tap #1` читает уже готовый mapping из page JSON
- этот mapping хранится как:
  - `source token -> target token index`

Это был главный практический вывод всей сессии.

### Что удалось подтвердить по инвариантам token mapping

На живых страницах подтверждено:

- one-to-one бывает, но не обязателен
- many-to-one разрешён
- strict `1:1 слово -> слово` не является контрактом

Примеры many-to-one:

- `The + Sunny -> Солнечное`
- `wakes + up -> просыпается`
- `The + sun + is -> Солнце`
- `He + is -> Он`
- `to + the -> на`

Также подтверждено:

- индекс `targetIndex` по source-потоку обычно монотонно идёт слева направо
- но допускаются редкие перестановки

Пример reorder:

- `Tom thinks` в source
- `думает Том` в target
- индексы на двух соседних source-токенах идут как:
  - `Tom -> 38`
  - `thinks -> 37`

То есть strict monotonicity не гарантируется.

### Что удалось подтвердить по `sentences`

Поле `sentences` хранит стартовые индексы source-предложений внутри `tokens1`.

Примеры:

- `page_1.sentences = [0, 5, 11, 15, 18, 28, 33, 38]`
- `page_2.sentences = [0, 3, 6, 11, 15, 20, 25, 36]`

После разрезания по ним получаются реальные source-sentence фрагменты.

Дальше проверено, что внутри source sentence:

- набор `targetIndex` почти всегда образует непрерывный span по `tokens2`

Примеры:

- `Tom wakes up at 7:00 AM.` -> target span `(4..8)` -> `Том просыпается в 7:00 утра.`
- `He is happy.` -> `(11..12)` -> `Он счастлив.`
- `Tom makes breakfast.` -> `(3..5)` -> `Том готовит завтрак.`

Что это дало:

- у них слово-уровень сидит на sentence-first scaffold
- runtime reader почти наверняка ограничивает фокус текущим sentence window

### Что удалось подтвердить по `score`

Наблюдаемые значения:

- `100`
- `0`
- `null`

Факты:

- это не случайные значения
- они системно повторяются
- они коррелируют с типом соответствия

Подтверждённые паттерны:

- `100`
  - content words с прямым или близким lexical match
  - примеры:
    - `makes -> готовит`
    - `breakfast -> завтрак`
    - `sun -> Солнце`
    - `bright -> яркое`
    - `transformed -> изменило`

- `null`
  - токен не получает самостоятельного lexical hit и приклеивается к соседнему смысловому узлу
  - часто это function words
  - примеры:
    - `the`
    - `of`
    - `is`
    - `has`
    - `a`
    - `up`

- `0`
  - соответствие есть, но не выглядит как сильный буквальный lexical hit
  - примеры:
    - `In -> В`
    - `significantly -> существенно`
    - `way -> способ`
    - `made -> принимаются`
    - `cost -> ущерб`
    - `ensure -> обеспечения`

Граница вывода:

- точный внутренний смысл `100 / 0 / null` не восстановлен на уровне формулы
- но разделение на:
  - strong lexical
  - attached / inherited
  - weaker / transformed
  уже очень вероятно

### Главный итог по пониманию механики

На конец сессии картина такая:

- runtime `tap #1` уже понят довольно хорошо
- build-stage alignment понят на уровне контура и основных типов данных
- точная scoring / selection formula для выбора лучшего `targetIndex` ещё не восстановлена до конца

Если грубо по уровню уверенности:

- как работает `tap #1` в reader runtime:
  - примерно `90-95%`
- как строится общий sentence/word alignment pipeline:
  - примерно `65-75%`
- как именно выбирается лучший target token и что точно значат все score-классы:
  - ещё не `100%`

### Что подтверждено точно

- `tap #1` работает по заранее сохранённому page payload
- mapping хранится как `source token -> target token index`
- `sentences` задаёт границы source-предложений
- many-to-one разрешён
- reorder допускается
- build-stage использует:
  - sentence alignment
  - word alignment
  - priors по lexical/fertility/jump

### Что остаётся неполным

- точная формула выбора `targetIndex`
- точный смысл `score = 100 / 0 / null`
- содержимое и роль `align_token`
- полная схема и наполнение внутренних `main_words / secondary_words / counts`
- точный reader-код, который превращает `targetIndex` в визуальный фокус

### Зачем эта запись важна дальше

- она фиксирует уже не гипотезы, а доказанные данные по `2Books`
- это даёт основание продолжать анализ глубже:
  - разбирать `score`
  - разбирать `monotonic breaks`
  - пытаться восстановить rule-set выбора `targetIndex`
- и при необходимости использовать найденный runtime contract как референс для будущего проектирования отдельного tap-layer в LEXO

До этой сессии было понятно:

- build финальной книги локальный

Это серьёзно усилило тезис, что основной pipeline действительно считается локально.

### Что отдельно проверили и отбросили

  - в пойманных случаях осталась пустой

  - после захвата `input/` и `parse/` она стала существенно слабее

Не удалось пока зафиксировать только следующий локальный переход:


Именно этот слой остаётся следующим объектом исследования.

### Что делать дальше

При продолжении нужно:

1. Повторить автодамп `app_flutter/ebooks/<bookId>` с ещё более частым polling.
2. Параллельно мониторить:

## Дополнение: проверка локального build-path через `adb root`, cache, `logcat` и transient staging

### Зачем понадобился этот дополнительный этап

После первичного reverse-анализа оставалась ключевая развилка:

- часть строк в `libapp.so` намекала на network endpoints
- пользователь утверждал, что перевод и alignment у `2Books` происходят локально
- нужно было не спорить гипотезами, а проверить это на живом процессе импорта книги

Цель этого дополнительного этапа:

- убедиться, что локальный pipeline реально существует
- отделить реальные данные от ложных чтений из-за permission-ошибок
- поймать максимально ранние промежуточные стадии построения книги

### Метод 1. Проверка того, что мы читаем реальные файлы, а не ошибки доступа

Сначала выяснилось, что часть ранних pull-артефактов была недостоверна:

- при чтении некоторых файлов без `adb root`
- вместо содержимого в локальные дампы попадал текст permission-ошибки
- из-за этого маленькие размеры некоторых файлов вводили в заблуждение

Что сделали:

- перевели `adb` в root-режим
- повторно выгрузили:
  - `cache`
  - `databases`
  - `app_flutter`
- перепроверили размеры и содержимое тех же файлов уже в root-контуре

Почему это важно:

- только после `adb root` стало возможным опираться на реальные локальные EPUB и БД
- это убрало риск строить выводы на артефактах вида `Permission denied`

### Метод 2. Прямая проверка локального cache-слоя

После `adb root` были подтверждены реальные локальные исходники книг в:

- `/data/data/su.x2books.app/cache`

Подтверждённые файлы:

- `The-Bus-Driver.epub`
- `The-Sunny-Morning.epub`
- `B2.epub`
- `B2-.epub`
- `The Sunny Morning.txt`

Почему это важно:

- `The Bus Driver` в cache существует как реальный локальный EPUB
- при этом в финальном `pages/*.json.gz` у него уже есть русская сторона
- это сильно поддерживает локальный `import -> parse -> translate/align -> export` путь

### Метод 3. Повторная проверка `process.db` уже в root-контуре

После `adb root` была ещё раз выгружена реальная:

- `/data/data/su.x2books.app/app_flutter/parallel/process.db`

Факты:

- размер БД оказался реальным, а не артефактом ошибки доступа
- но таблицы всё равно были пустыми:
  - `align = 0`
  - `main_book = 0`
  - `secondary_book = 0`
  - `main_toc = 0`
  - `secondary_toc = 0`
  - `meta = 0`

Что это дало:

- `process.db` подтверждена как существующая staging-база
- но в захваченных локальных прогонах она не была носителем активного build-state
- значит реальный пойманный путь шёл не через наполненную `process.db`

### Метод 4. Live `logcat` во время импорта книги

Был поднят фильтрованный `logcat` во время живого импорта новой книги в эмуляторе.

Что удалось поймать:

- копирование исходного EPUB в cache через `FileDialog`
- распаковку EPUB через `FlutterArchivePlugin`
- создание временного рабочего пути вида:
  - `/data/user/0/su.x2books.app/app_flutter/ebooks/<bookId>/input/EN.epub`
- строку:
  - `onlinePageTranslated`
- сообщения про:
  - `Local translate success`
  - `Failed local translate`
  - `Waiting for a global translate lock`
  - `translateWithEngine: invalid lengths`
- а также сетевые таймауты к `2books.su`

Что из этого важно интерпретационно:

- наличие сетевых таймаутов само по себе не доказывает server-side перевод
- одновременно были пойманы реальные локальные стадии:
  - cache
  - unpack
  - parse

- поэтому network-следы были зафиксированы как сопутствующие, но не как доказательство server-only pipeline
