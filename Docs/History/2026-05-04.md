### Самая важная находка всей сессии

Удалось поймать две реальные версии одного и того же `pages/0.json.gz`.

#### Ранняя версия `709` байт

Содержала:

- `version = 2`
- `sentences`
- `tokens1`
- `footnotes1 = []`
- `footnotes2 = []`

Но ещё не содержала:

- `tokens2`
- `translator`
- `targetIndex`
- `score`

Формат source tokens в ранней версии:

- `["The",""," ",null,null]`
- `["Bus",""," ",null,null]`
- `["Driver","","\n\n",null,null]`

То есть:

- source surface уже полностью собран
- sentence segmentation уже полностью собрана
- bilingual enrichment ещё не произошёл

#### Поздняя версия `1802` байта

Содержала:

- тот же `sentences`
- тот же `tokens1`
- `tokens2`
- `translator = google_mobile`
- `targetIndex`
- `score = 100 / 0 / null`

Формат финальных tokens:

- `["The",""," ",1,null]`
- `["Bus",""," ",1,100]`
- `["Driver","","\n\n",0,100]`

#### Доказанный вывод

`pages/*.json.gz` у `2Books` строится минимум в 2 стадии:

```text
Stage A:
source page skeleton
= tokens1(surface) + sentences

Stage B:
late bilingual enrichment
= tokens2 + targetIndex + 100/0/null + translator
```

### Обновлённая модель `tap #1`

Теперь модель выглядит так:

```text
1. import EPUB/TXT
2. unpack -> input/EN
3. parse -> parse/EN/content/*.txt
4. build source page skeleton
   - tokens1 surface
   - sentences
5. late bilingual enrichment
   - tokens2
   - targetIndex
   - 100 / 0 / null
   - translator
6. write final pages/*.json.gz
7. reader tap #1 reads final enriched page payload
```

### Что теперь известно точно

- `tap #1` не работает по realtime alignment
- `tap #1` не работает по раннему parse-layer
- `tap #1` не работает по source-only page skeleton
- `tap #1` читает уже финальный enriched page payload

- `sentences` рождается до bilingual enrichment
- `tokens1` как source surface рождается до bilingual enrichment
- `tokens2`, `targetIndex`, `100/0/null`, `translator` появляются одновременно на позднем этапе

### Что остаётся неизвестным

- точный внутренний алгоритм выбора `100` против `0`
- точный порог разрыва frame по `forward_gap`
- точный reader-алгоритм расширения одного `targetIndex` в финальный target-span
- содержимое и роль `align_token`
- живёт ли late enrichment целиком в памяти или в сверхкоротком промежуточном объекте, который ещё не пойман

### Итоговый статус расследования

Главный чёрный ящик теперь сужен до конкретного позднего слоя:

```text
source skeleton:
  tokens1(surface) + sentences
-> bilingual enrichment black box:
  tokens2 + targetIndex + 100/0/null + translator
-> final page payload
```

Это и есть центральный runtime/build слой, делающий `tap #1` возможным.

### Что добавлено

- новый Python hook-скрипт:
  - [scripts/capture_2books_frida_page_writes.py](/mnt/d/Programs/LEXO/scripts/capture_2books_frida_page_writes.py)
- новый Windows launcher:
  - [scripts/2books_capture/run_2books_frida_capture.bat](/mnt/d/Programs/LEXO/scripts/2books_capture/run_2books_frida_capture.bat)

### Что делает новый hook

- ждёт процесс `su.x2books.app`
- attach-ится к живому процессу через Frida
- хукает libc:
  - `open/open64/openat/openat64`
  - `write`
  - `close`
  - `rename/renameat`
- отслеживает реальные записи в:
  - `/app_flutter/books/.../pages/...`
- сохраняет не snapshot-и файлов, а именно реальные буферы `write()`

### Куда пишет результаты

- новый каталог прогонов:
  - `tmp/x2_frida_capture/run_YYYYMMDD_HHMMSS/`

Внутри:

- `summary.txt`
- `session.json`
- `events.jsonl`
- `payloads/`

### Зачем это нужно

- уйти от файлового polling как от основного инструмента
- поймать все реальные версии `pages/*.json.gz`, проходящие через runtime write-path
- проверить, существуют ли внутренние промежуточные версии между ранним `709B` и поздним `1802B`
- приблизиться к реальному late enrichment слою уже через hooking, а не только через post-factum snapshot-и

### Что уже подтвердили первые Frida-прогоны

- hook стабильно attach-ится к живому процессу `2Books`
- на runtime-уровне подтверждено, что late stage трогает:
  - `pages/0.json.gz`
  - `pages/0.json.gz.tmp`
- `.tmp` открывается как реальный write-target, а не как read-only артефакт

Это впервые подтвердило на hook-уровне:

- `2Books` использует временный output-файл для page payload
- путь записи финального payload проходит через `.tmp`

### Что не дало первое поколение hook

При наличии `.tmp` не были пойманы:

- `write`
- `pwrite`
- `writev`
- `rename`

Это дало новый вывод:

- реальная запись уходит ниже обычного libc write-path
- либо используется другой syscall/API
- либо нужен более низкий runtime capture

### Что добавлено во вторую итерацию hook

Поверх базового контура добавлены перехваты:

- `pwrite`
- `pwrite64`
- `writev`
- `fsync`
- `fdatasync`
- `ftruncate`
- `ftruncate64`
- `lseek`
- `lseek64`
- `unlink`
- `unlinkat`
- `mmap`
- `msync`
- `syscall` с разбором интересующих номеров

Также:

- логируются `open`-flags
- для writable-open на `.tmp` теперь снимается backtrace

### Текущий статус Frida-ветки

- Frida-контур уже стал отдельным полноценным слоем расследования
- следующий прогон должен показать:
