# 2026-04-30

## Сессия: Анализ рассинхрона persisted QA и hard-block final selection для критичных semantic defects

### Контекст

- по 3 живым книгам (`Max’s New Day`, `The Bus Driver`, `The Sunny Morning`) был выполнен повторный QA-анализ критичных translation ошибок:
  - лишние слова
  - недостающие слова
  - буквальная неправильность перевода
  - задвоения слов

- подтверждено, что проблема состоит из двух разных слоёв:
  - candidate selection всё ещё мог сохранять плохой `merge`-кандидат как `best available`
  - persisted QA в `segments` мог расходиться с тем, что текущий `evaluate_segment_translation(...)` считает сейчас

### Что было подтверждено анализом

- у сегмента `Nick says, “Good morning!” to everyone.` после обновления книг:
  - `people`-кейс уже исправился через `nbest_candidate_won`
  - кейс `to everyone` + `доброе доброе` остался
  - в базе сегмент был сохранён как:
    - `winner_reason = merged_candidate_best_available`
    - `provider_used = Helsinki-NLP/opus-mt-en-ru+merge`

- отдельной проверкой по 3 книгам найден рассинхрон между persisted QA и текущим кодом:
  - проверено `84` сегмента
  - расхождений найдено `43`
  - это подтверждает, что persisted verdict в `segments` нельзя считать автоматически консистентным после изменения QA-логики

### Что изменено

- обновлён [engine/storage.py](/mnt/d/Programs/LEXO/engine/storage.py)
  - добавлен `_has_blocking_retry_reason(...)`
  - добавлен `_finalize_selected_payload(...)`
  - теперь финальный выбранный кандидат с blocking semantic defects больше не сохраняется как `pass`
  - для таких сегментов финальный persisted contract переводится в:
    - `quality_status = fail`
    - `alignment_confidence = 0.0`
    - `quality_score <= 45`

- blocking-набор ограничен только подтверждёнными content defects:
  - `extra_content`
  - `missing_head_noun`
  - `missing_participant`
  - `missing_object`
  - `missing_recipient`
  - `missing_destination`
  - `substituted_predicate`
  - `substituted_head_noun`
  - `substituted_role`
  - `substituted_participant`
  - `local_duplicate_word`
  - `local_duplicate_phrase`

- verb-эвристики вроде:
  - `missing_predicate`
  - `suspicious_verb_choice`
  не переводятся в hard-block сами по себе
  - это сделано специально, чтобы не ломать разрешённый near-paraphrase кейс `Tom goes home. -> Том возвращается домой.`

- в [engine/storage.py](/mnt/d/Programs/LEXO/engine/storage.py) также убрано безусловное преимущество `+merge` при ranking
  - теперь merge получает bonus только если это clean candidate без `retry_reason_flags`
  - это сохраняет полезный hybrid merge path
  - но не даёт плохому merge-кандидату выигрывать просто из-за типа происхождения

- обновлён [scripts/check_pipeline_regressions.py](/mnt/d/Programs/LEXO/scripts/check_pipeline_regressions.py)
  - для blocking semantic defects добавлены проверки, что persisted итоговый сегмент сохраняется как `quality_status = fail`
  - при этом `decision_status = retry_required` сохраняется как сигнал о необходимости повторного подбора

### Что проверено

- выполнен полный regression suite:
  - `python3 scripts/check_pipeline_regressions.py`
- результат:
  - весь regression suite проходит

### Итог

- плохой merge-кандидат с критичной content-потерей или дублем больше не должен сохраняться как normal final `pass`-результат
- clean merge path сохранён
- при этом системная проблема persisted QA drift по уже сохранённым книгам остаётся отдельным подтверждённым слоем и требует отдельной политики полного rebuild/invalidation

## Сессия: Скрипт-имитация candidate pool для `Nick says, "Good morning!" to everyone.`

### Что сделано

- добавлен [scripts/debug_segment_candidates_simulated.py](/mnt/d/Programs/LEXO/scripts/debug_segment_candidates_simulated.py)
  - локальный debug-скрипт без real provider
  - имитирует `base / nbest / merge` для одного проблемного сегмента
  - печатает:
    - все candidate traces
    - `quality_status`
    - `decision_status`
    - `quality_score`
    - `quality_flags`
    - `retry_reason_flags`
    - финальный выбранный вариант

### Какие сценарии покрыты

- `bad_pool_like_current_issue`
  - только плохие варианты без сохранённого `recipient`

- `merge_duplicate_pool`
  - пул с потенциальным duplicate/merge шумом

- `good_recipient_pool`
  - пул, в котором есть нормальный вариант с `всем`

### Что показал прогон

- если в пуле нет нормального варианта с `recipient`, selector оставляет лучший из плохих, но теперь финальный persisted contract остаётся `fail + retry_required`
- если в пуле есть нормальный вариант с `всем`, он выигрывает как `nbest_candidate_won`
- merge-path действительно может порождать большое количество мусорных hybrid-кандидатов даже на коротком speech сегменте
