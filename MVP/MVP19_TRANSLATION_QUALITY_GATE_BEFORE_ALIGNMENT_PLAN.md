# MVP19: Quality Gate Перевода До Alignment

## Цель

Перестроить pipeline так, чтобы сначала проверять качество перевода каждого сегмента, выбирать лучший `target_text`, и только потом строить `word alignment`.

## Проблема

Сейчас pipeline принимает первый полученный перевод сегмента как валидный. Из-за этого:

- в базу попадает плохой `target_text`
- затем `alignment` строится уже по испорченному переводу
- в UI это выглядит как ошибки `слово = слово`, хотя корень проблемы выше

Примеры уже найденных ошибок:

- дубли и loop-output на старом `nllb33`
- смысловые промахи:
  - `calls` -> `звонит`
  - `wags his tail` -> `валяет хвост`
  - `goes home` -> `ездит домой`
  - `sun goes down` -> `солнце падает`
- сдвиг времени:
  - present -> future
  - present -> past

## Новый целевой порядок pipeline

1. Разбить книгу на сегменты.
2. Для каждого сегмента выполнить `EN -> RU`.
3. Для каждого сегмента выполнить quality-check.
4. Если качество плохое или среднее:
   - запросить альтернативные варианты перевода этого же сегмента
   - при необходимости сделать retry в другом decode-режиме
   - при необходимости сделать fallback на другой provider
5. Выбрать лучший `target_text`.
6. Сохранить итоговый перевод сегмента.
7. Только после этого запускать `word alignment`.
8. Если качество сегмента низкое, alignment либо пропускать, либо помечать как `low confidence`.

## Главная идея

Проверять не только подозрительные сегменты, а каждый сегмент.

## Проверка качества сегмента

Для каждого сегмента ввести quality gate из нескольких слоёв.

### 1. Технические проверки

Ловят явный брак:

- повтор токенов и фраз
- слишком много английского в русском
- мусорные символы
- слишком короткий или слишком длинный `target`
- пустой или почти пустой перевод
- подозрительное копирование source в target

### 2. Semantic check через back-translation

Для каждого сегмента:

- `EN -> RU`
- затем `RU -> EN`
- сравнить исходный EN и обратный EN

Это не проверка `строка равна строке`.
Это проверка `смысл достаточно близок`.

### 3. Лингвистические флаги

Ловят типовые ошибки:

- явный сдвиг времени
- плохой выбор глагола
- сломанная русская фраза
- калька, которая ломает смысл
- бытовые и narrative-глаголы, переведённые не в тот смысл

## Что хранить по каждому сегменту

Нужно добавить служебные поля или внутреннюю структуру оценки:

- `source_text`
- `target_text`
- `back_translation`
- `quality_score`
- `quality_flags`
- `translation_attempt_count`
- `provider_used`
- `alignment_confidence`

Примеры `quality_flags`:

- `repetition`
- `english_leftover`
- `semantic_drift`
- `bad_russian`
- `tense_shift`
- `suspicious_verb_choice`
- `length_mismatch`

## Логика принятия решения

Для каждого сегмента:

1. Если score хороший:
   - сохранить перевод
   - запустить alignment

2. Если score средний:
   - запросить ещё 2-3 варианта перевода
   - пересчитать quality для каждого
   - выбрать лучший
   - alignment строить, но можно понизить confidence

3. Если score плохой:
   - retry в более строгом decode-режиме
   - если не помогло, fallback на другой provider
   - если всё ещё плохо, сохранить лучший из кандидатов как `low confidence`
   - alignment не строить или пометить как ненадёжный

## Альтернативные варианты перевода

Нужно поддержать `n-best` стратегию:

- для каждого сегмента можно получить 2-4 варианта перевода
- каждый вариант отдельно прогонять через quality gate
- выбирать лучший по score, а не первый

Это важнее, чем переводить каждое слово отдельно.

## Что не делать как основной путь

Не использовать перевод каждого слова отдельно как основной способ исправления.

Причина:

- отдельное слово теряет контекст
- фразовые глаголы и короткие реплики ломаются
- `word-by-word` полезен для диагностики, но не как основной pipeline

## Сегменты нужно разделить по типам

Нужна классификация сегментов до перевода:

- `heading_title`
- `chapter_heading`
- `quote_dialogue`
- `short_phrase`
- `sentence`
- `long_sentence`

Это нужно, потому что короткие title/dialogue сегменты и обычные предложения ведут себя по-разному.

## Политика по типам сегментов

### 1. `heading_title`, `chapter_heading`, `short_phrase`

- жёстче quality gate
- чаще использовать n-best
- быстрее уходить в fallback

### 2. `quote_dialogue`

- отдельно следить за глаголами речи
- отдельно следить за английскими остатками и короткими повторами

### 3. `sentence`, `long_sentence`

- сильнее учитывать semantic drift и tense shift

## Alignment после перевода

Alignment запускать только после выбора финального `target_text`.

Правила:

- если `quality_score` высокий: обычный alignment
- если `quality_score` средний: alignment с флагом `low confidence`
- если `quality_score` низкий: alignment пропустить или не показывать как `word = word`

## Что даст быстрый практический эффект

Первый этап даст максимальный результат:

1. quality gate на каждом сегменте
2. back-translation `EN -> RU -> EN`
3. 2-3 альтернативных перевода на сегмент
4. выбор лучшего кандидата
5. только потом alignment

## Этапы внедрения

1. Ввести внутренний quality-check для каждого сегмента.
2. Добавить back-translation и semantic score.
3. Добавить поддержку альтернативных кандидатов перевода.
4. Добавить выбор лучшего кандидата.
5. Привязать alignment к качеству финального сегмента.
6. Добавить логирование причин брака по сегменту.
7. Потом уже улучшать сами модели и словари рискованных паттернов.

## Критерий готовности

Система считается внедрённой, когда:

- каждый сегмент проходит quality-check до сохранения
- плохой первый перевод не попадает в базу без retry/fallback
- `alignment` строится только по финальному переводу
- для каждого сегмента можно объяснить:
  - какой перевод выбран
  - почему он выбран
  - какой у него score
  - почему alignment построен или пропущен
